    Notes & sources

    What this depicts

    HashCSR combines a hash lookup with a compressed sparse row (CSR) layout: each group owns a contiguous segment of build-row IDs. Join probes find the segment and expand its members.

    Join and groupby implement the count → scan → place technique with separate HashCSR builds. Join retains a packed lookup directory with representative-row offsets. Groupby records per-row ranks, compacts occupied groups, and reduces a dense CSR. The join diagrams follow the packed, representative-row-indexed design in cuDF PR #24231, revision c118ec760e6d. Capacity sizing, starting slots, and join allocation lifetimes follow cuDF PR #24331, merged revision 6bbcaedd6bdc.

    An earlier branch tried unifying the previous join and groupby implementations while preserving their algorithms. Relatively small changes to the shared control flow affected performance. For join, a shared probe/store structure increased register usage from 34 to 36 per thread in one build specialization. For groupby, moving rank writes into a common store extended variable lifetimes and increased register usage from 64 to 66 per thread; that intermediate version slowed one sampled keys-only workload by roughly 7%. That comparison predates a common key size: join HashCSR used 64-bit keys, and groupby used 32-bit keys. Now that both use the same key size, a unified HashCSR could be reevaluated once the groupby migration lands.

    The CSR connection

    “uses concepts taken from sparse graph representations”

    — Green (2021), published abstract.

    This is the central connection: represent each bucket or group with an offset-delimited adjacency range instead of a linked list of individual entries.

    Capacity is computed before hashing

    Let N be the number of build rows, including duplicates, and let α be the requested load factor (0 < α ≤ 1; default 0.5). The host computes:

    R = max(N + 1, ceil(N / α))

    • Capacity is R.
    • The starting slot is __umulhi(__brev(hash), capacity): reverse the hash’s bits, multiply by capacity, and keep the high 32 bits of the product, giving a slot in [0, capacity). Linear probing wraps from the last slot to slot 0.

    For this example, N = 6 and α = 0.5, so R = max(7, 12) = 12 and capacity is 12 slots. At α = 0.75, capacity is 8; at α = 1, capacity is 7.

    The N + 1 term leaves at least one empty slot even if every row is unique. Distinct-key count is not needed before construction: budgeting from all six rows is conservative. Our three distinct keys ultimately occupy only 3 / 12 = 25% of the directory.

    Capacity determines the range of starting slots and the slot allocation, not the row-bit width. The packed slot still needs only bit_width(6) = 3 row bits, even though there are 12 hash slots. Capacity sizing uses host metadata, not a GPU kernel or a distinct-count pass.

    Source: hash_csr_capacity and initial_slot as of cuDF PR #24331. This is the cuDF variant’s sizing policy, not HashGraph’s load-factor policy. The requested size must fit in uint32_t; otherwise it throws.

    HashGraph and this HashCSR variant

    HashGraph groups inputs by hash bucket, including unequal keys that collide. This presentation’s HashCSR variant uses an open-addressed directory of equal-key groups. Equality checks separate A and B even when their starting slots collide.

    The shared principle is count → scan → place into contiguous ranges. The paper’s Algorithm 1 has separate parallel loops for hashing and counting. The join implementation fuses insertion and counting, packs 32-bit slots, indexes offsets by representative row, and reuses cumulative ends as decrementing fill cursors. The groupby implementation saves ranks during insertion and compacts groups before filling a dense CSR.

    Compare Green, preprint §§3.1–3.2, Algorithm 1, pp. 3–4, with the cuDF kernels.

    Count before assigning storage

    “the number of instances that each hash value appears in the original input.”

    — Green, preprint §3.2, step 3, p. 4.

    HashGraph counts members per hash bucket. Here, atomic counts are indexed by an equal-key group’s representative row. Both counts answer the storage question: how many entries must this segment hold?

    Counts become segment boundaries

    “A prefix sum array is computed.”

    — Green, preprint §3.2, step 4, p. 4; Algorithm 1, p. 3.

    The prefix sum partitions the contiguous entry array according to the counts. This variant first produces cumulative ends; the fill kernel turns them into exclusive starts by decrementing its cursors.

    Contiguous ranges, not pointer chains

    “the entries for a specific hash value are in consecutive memory.”

    — Green, preprint §3.2, HashGraph Collision Management, p. 4.

    The paper’s placement step uses offsets and an atomic relative position (§3.2, step 6). Our example applies the locality principle to equal-key groups: all A row IDs occupy one interval, all B row IDs another. The packed directory itself still uses linear probing.

    Probe a second input

    “the values from a second input are looked up within the hash table created from the first input.”

    — Green, preprint §3.4, pp. 5–6.

    This describes the build/probe relationship in the join scene. The paper also introduces a different two-HashGraph, list-intersection probe (Algorithm 3); that is not the one-index probe/count → scan → retrieve path illustrated here.

    Retrieval iterates over output slots

    For output slot k, an upper bound over the probe-output offsets finds the probe row p. The local match index is k − out_offsets[p]; adding it to the build group’s start selects the matching build row ID. Repeated offsets skip probes with zero matches.

    A warp first looks up its output chunk’s endpoints. If both belong to one probe row, lanes reuse that row; otherwise they search within the endpoint probe range. The slide uses three-output chunks to expose both cases. Actual chunk sizes depend on output size and launch configuration, with lanes processing multiple outputs.

    Sources: hash_csr_retrieve_kernel; probe, scan, and retrieval allocation lifetimes.

    Groupby builds dense groups

    Groupby stores only a representative row index in each 32-bit directory slot; unlike join, it packs no hash fingerprint. Its build kernel records a count index and within-group rank for each row. For this six-row example, capacity is 12 and counts use representative row indices. Positive counts select key_rows = [0,1,3], whose counts [3,2,1] scan into dense offsets [0,3,5,6]. The counts buffer is then reused for group starts. Fill uses each saved index and rank to place row IDs.

    The illustrated ranks give grouped_rows = [0,2,5,1,4,3]. Representative winners and within-group order depend on GPU scheduling. The groupby starts from the input rows and owns these buffers independently of the join.

    At n ≥ 2²¹, groupby estimates distinct keys from a sample and may use a smaller table. When capacity is at most n, counts use directory slot indices; bounded probing can trigger a retry at full capacity. The all-singleton path directly produces identity row order. These paths have their own allocation lifetimes.

    Sources at d367924abaa9: group_keys and build and fill kernels.

    Reduce each dense CSR segment

    “group-by and aggregation”

    — Green, preprint §1, p. 1, among the applications of hash tables, alongside inner join.

    Groupby reduces payloads through grouped row IDs. Groups of at most 32 rows use reduce_small_groups_kernel, with one thread per group. Larger groups use warp reductions; groups over 1024 rows use chunk partials followed by a second reduction. The three example groups take the small-group path and produce int64 sums from int32 payloads. Gathering keys from representative rows completes the three-row output.

    Sources: small-group reduction, segment scheduling, and indirect loads and SUM output.

    Groupby dispatches by segment length

    The additional slide uses a different, illustrative workload: three groups of 3, 64, and 2050 rows. The 3-row group takes the one-thread path. The 64-row group gets one warp. The 2050-row group is divided into three chunks of 1024, 1024, and 2 rows; one 256-thread block reduces each chunk into an int64 partial, and another block reduces the three partials to the final SUM. The thresholds compare each segment’s length, not average group size. The 32- and 1024-row cutoffs, block size, and chunk scheduling are implementation choices at revision d367924abaa9 and may change with benchmarking. These paths operate on the groupby CSR already built; they do not rebuild it.

    For this one-column, non-null int32 SUM, let H be the number of groups wider than 32, L the number wider than 1024, and Q the total chunks of long groups. Here n=2117, G=3, H=2, L=1, Q=3. At the chunk-reduction stage, scheduling retains warp_groups[H], group_chunks[L+1], chunk_ranges[Q] (two int32 endpoints per range), and chunk_order[Q]; the reducer allocates partials[Q] of int64. first_rows[Q] and the sort workspace exist during chunk scheduling, but are released before the partials are allocated; the panel does not sum these different moments. The returned sums are excluded.

    Sources at d367924abaa9: group selection and chunk scheduling; one-thread, warp, and two-pass block reductions.

    Two offsets define a range

    “The end of the adjacency array is the offset to the next vertex.”

    — Green, preprint §3.1, p. 3; Figure 1, p. 4.

    Join locates a representative row r and enumerates values[offsets[r]:offsets[r+1]]; equal adjacent offsets describe an empty segment. Groupby assigns dense group IDs g and reduces payloads through grouped_rows[group_offsets[g]:group_offsets[g+1]].

    Animation steps ≠ kernel launches

    • Host setup: capacity is computed from the row count and requested load factor before the GPU build. The Size slide does not represent a GPU kernel.
    • Build kernel: hashing, insertion/equality checks, and atomic counting are fused in hash_csr_build_count_kernel. The Hash and Count slides illustrate hashing/insertion and counting within this one kernel, not successive launches.
    • Device scan: cub::DeviceScan::InclusiveSum runs after build and before fill. A library scan is a separate GPU stage and may launch multiple kernels.
    • Fill kernel: numeric keys hash/find their representative again, decrement a cursor, and scatter row IDs in hash_csr_build_fill_kernel. The cached variant reads the representative instead. Cursor updates produce the final offsets in the same kernel.
    • Join: hash_csr_probe_count_kernel fuses probe hashing, lookup, and match counting. A separate device scan computes output offsets; hash_csr_retrieve_kernel then expands ranges into pairs.
    • Groupby build: hash_csr_build_kernel fuses insertion, counting, and rank assignment. Device algorithms compact group IDs, copy representatives, scan counts, and scatter group starts. hash_csr_fill_kernel then places rows using saved positions.
    • Groupby reduction: scheduling inspects segment sizes first. The six-row example uses one small-group reduction kernel with indirect payload loads, followed by a device gather of output keys. The alternate workload shows direct warp reductions for medium groups and two block-reduction passes for long groups.

    Device memory accounting

    The panels define their variables above the allocations: n is the number of build rows (6 except on the alternate dispatch slide), m the number of probe rows (3), J the number of join outputs (5), G the number of groups (3), and cap the number of directory slots (12). Keys A–D and payloads are non-null int32 values. A groupby position contains a uint32 count index and an int32 rank. The bottom row sums the listed allocations live at that stage that are not returned to the caller, including the join directory. Final output columns are listed separately.

    Sizes are requested allocation capacities. The W terms denote library workspace sizes obtained for the actual device, library version, and operation. The figures cover the listed buffers; input storage, table preprocessing and column descriptors, allocator rounding or reserved pool memory, and host storage are outside this accounting. Lifetimes, rather than a sum of all allocations ever made, determine live memory.

    • Join: counts, ends, and starts share the (n+1) × sizeof(int32) offsets allocation. The build scan releases its workspace before allocating row IDs. Slots, offsets, and row IDs form the join index; it is temporary to the join operation despite living across several slides. Keys containing strings or lists additionally cache n × sizeof(int32) representatives during construction.
    • Probe and retrieve: match counts, an auxiliary uint64 counter, and scan workspace are released before output allocation. Group IDs and int64 output offsets remain through retrieval. The two final pair columns occupy 2J × sizeof(int32), outside the temporary-storage total.
    • Groupby build: the directory is released after build on this representative-counting path. group_slots selects G indices but retains capacity for n until released before fill. Its selection workspace is released after copy_if, before key_rows is copied. The scan workspace is released after scanning counts; then scatter reuses counts as group starts. Fill allocates grouped row IDs after releasing group_slots.
    • Groupby reduction: segment scheduling uses library workspace before the reduction. The small-group path writes sums directly to the G × sizeof(int64) output. Key gathering produces G × sizeof(int32) keys; grouping arrays live through the gather. The dispatch slide counts the extra scheduling arrays and chunk partials at the chunk-reduction stage. Nullable inputs add validity storage.

    Allocation sources: join index, join build lifetimes, probe/retrieve lifetimes, and groupby temporary resources and output keys.

    Example & conventions

    Build rows r0…r5: (A,12), (B,7), (A,8), (C,5), (B,3), (A,10). Probe rows p0…p2: B, A, D. All keys and values are non-null.

    • Fixed illustrative 32-bit hashes A→0xECC1EF1D, B→0x62F5012D, C→0x0BEF92C6 show mixed bits across the whole word. They are chosen so that __umulhi(__brev(hash), 12) gives starting slots 8, 8, 4, preserving the A/B probe collision. These are not cuDF’s real hash outputs. Each displayed fingerprint shows its first and last three bits; the ellipsis hides the 23 middle bits, which may contain both zeros and ones.
    • One possible execution chooses representatives r0, r1, r3. Threads race using a device-scoped atomic compare-and-swap (CAS) on 32-bit slots in global memory. The first row to claim an empty slot becomes that key’s representative; equal rows reuse its stored row index. A collision with a different key continues probing. The winner is scheduling-dependent, not necessarily the lowest row index. This is distinct from the warp-aggregated atomic add that counts group members. See hash_table_ref::insert.
    • The packed slot combines two independently sourced fields. Its 29 high bits retain part of the original hash as a fingerprint: a quick mismatch filter that avoids loading and comparing unrelated keys. Its three low bits identify the representative build row, which locates both the original key and the group’s CSR segment. A fingerprint match still requires a full key comparison; it is not proof of equality. The row bits are neither hash bits nor a hash-table slot number.
    • For C, hash = 0x0BEF92C6 and the representative is r3. Retain the 29-bit fingerprint 00001011111011111001001011000, discard the hash’s low bits 110, and replace them with row index 011. Thus (0x0BEF92C6 & ~7) | 3 = 0x0BEF92C3. The full hash still determines the starting slot; only its stored representation is packed.
    • Any similar-looking patterns in the fingerprint and row bits are coincidental, not duplicated information. The low field comes from the representative row index, never from copying fingerprint bits. For example, B’s original low hash bits 101 are replaced by row index 001.
    • The six-row diagram shows the resolved stored word for each input, not six separately stored entries. Duplicates reuse the winning representative: r2 and r5 use r0’s bits 000; r4 uses r1’s bits 001. A resolves to 0xECC1EF18, B to 0x62F50129, and C to 0x0BEF92C3: only three directory entries.
    • Six build rows (indices 0–5) need three row bits. In general, bit_width(N) row bits leave 32 − bit_width(N) fingerprint bits. This keeps the all-ones row index outside [0, N), so the all-ones 32-bit slot can represent empty. The key itself stays in the original row, not in the packed slot.
    • Counts include a trailing zero. An inclusive scan creates cumulative ends; atomic decrement-and-scatter transforms these into exclusive starts. Nonrepresentative rows retain zero-length segments.
    • Numeric keys find their representative again during fill. Keys containing strings or lists cache the representative to avoid repeating costly hashing and comparisons.
    • In groupby, segment lengths give COUNT; reducing each segment’s payloads can compute SUM, MIN, or MAX. This example uses SUM and shows only occupied groups.
