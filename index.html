    Notes & sources

    What this depicts

    HashCSR combines a hash lookup with a compressed sparse row (CSR) layout: each group owns a contiguous segment of build-row IDs. Join probes find the segment and expand its members.

    Join and groupby share the same HashCSR construction: build, scan, fill. Only the consumer changes. Join probes the index and expands matches; groupby traverses its occupied segments and reduces payloads. The join diagrams follow the packed, representative-row-indexed design in cuDF PR #24231, revision c118ec760e6d.

    Research reference

    Oded Green. 2021. HashGraph—Scalable Hash Tables Using a Sparse Graph Data Structure. ACM Transactions on Parallel Computing 8(2), 1–17. doi:10.1145/3460872.

    The abstract excerpt below is from the published abstract. Other quotations and section/page locators refer explicitly to the author’s open 2019 preprint, arXiv:1907.02900v1, not to the journal’s pagination. Quotations are embedded here for offline reading.

    The CSR connection

    “uses concepts taken from sparse graph representations”

    — Green (2021), published abstract.

    This is the central connection: represent each bucket or group with an offset-delimited adjacency range instead of a linked list of individual entries.

    Capacity is computed before hashing

    Let N be the number of build rows, including duplicates, and let α be the requested load factor (0 < α ≤ 1; default 0.5). The host computes:

    R = max(N + 1, ceil(N / α))

    • If α ≤ 0.5, capacity is R, without power-of-two rounding.
    • If α > 0.5, capacity is bit_ceil(R): the smallest power of two at least as large as R.

    For this example, N = 6 and α = 0.5, so R = max(7, 12) = 12 and capacity is 12 slots. At α = 0.75, R = 8 and capacity is 8; at α = 1, R = 7 rounds up to 8.

    The N + 1 term leaves at least one empty slot even if every row is unique. Distinct-key count is not needed before construction: budgeting from all six rows is conservative. Our three distinct keys ultimately occupy only 3 / 12 = 25% of the directory.

    Capacity determines the hash modulus and slot allocation, not the row-bit width. The packed slot still needs only bit_width(6) = 3 row bits, even though there are 12 hash slots. Capacity sizing uses host metadata, not a GPU kernel or a distinct-count pass.

    Source: hash_csr_capacity in PR #24231. This is the cuDF variant’s sizing policy, not HashGraph’s load-factor policy. This revision also checks that both the requested size and its power-of-two round-up fit in uint32_t; otherwise it throws.

    HashGraph and this HashCSR variant

    HashGraph groups inputs by hash bucket, including unequal keys that collide. This presentation’s HashCSR variant uses an open-addressed directory of equal-key groups. Equality checks separate A and B even when their starting slots collide.

    The shared principle is count → scan → place into contiguous ranges. The paper’s Algorithm 1 has separate parallel loops for hashing and counting; the fused build kernel shown here, packed 32-bit slots, representative-row offsets, and decrementing fill cursors are implementation details of the cuDF variant, not claims about the paper’s kernel boundaries.

    Compare Green, preprint §§3.1–3.2, Algorithm 1, pp. 3–4, with the cuDF kernels.

    Count before assigning storage

    “the number of instances that each hash value appears in the original input.”

    — Green, preprint §3.2, step 3, p. 4.

    HashGraph counts members per hash bucket. Here, atomic counts are indexed by an equal-key group’s representative row. Both counts answer the storage question: how many entries must this segment hold?

    Counts become segment boundaries

    “A prefix sum array is computed.”

    — Green, preprint §3.2, step 4, p. 4; Algorithm 1, p. 3.

    The prefix sum partitions the contiguous entry array according to the counts. This variant first produces cumulative ends; the fill kernel turns them into exclusive starts by decrementing its cursors.

    Contiguous ranges, not pointer chains

    “the entries for a specific hash value are in consecutive memory.”

    — Green, preprint §3.2, HashGraph Collision Management, p. 4.

    The paper’s placement step uses offsets and an atomic relative position (§3.2, step 6). Our example applies the locality principle to equal-key groups: all A row IDs occupy one interval, all B row IDs another. The packed directory itself still uses linear probing.

    Probe a second input

    “the values from a second input are looked up within the hash table created from the first input.”

    — Green, preprint §3.4, pp. 5–6.

    This describes the build/probe relationship in the join scene. The paper also introduces a different two-HashGraph, list-intersection probe (Algorithm 3); that is not the one-index probe/count → scan → retrieve path illustrated here.

    A shared structure, multiple consumers

    “group-by and aggregation”

    — Green, preprint §1, p. 1, among the applications of hash tables, alongside inner join.

    Groupby reduces the payloads in each CSR segment using an aggregation operator. This example uses SUM. The results and fused load/reduce illustration are this presentation’s worked example, not a quoted groupby kernel from the paper.

    Two offsets define a range

    “The end of the adjacency array is the offset to the next vertex.”

    — Green, preprint §3.1, p. 3; Figure 1, p. 4.

    For representative row r, this becomes values[offsets[r]:offsets[r+1]]. Join enumerates that interval; groupby reduces its payloads. Equal adjacent offsets describe an empty segment.

    Animation steps ≠ kernel launches

    • Host setup: capacity is computed from the row count and requested load factor before the GPU build. The Size slide does not represent a GPU kernel.
    • Build kernel: hashing, insertion/equality checks, and atomic counting are fused in hash_csr_build_count_kernel. The Hash and Count slides illustrate hashing/insertion and counting within this one kernel, not successive launches.
    • Device scan: cub::DeviceScan::InclusiveSum runs after build and before fill. A library scan is a separate GPU stage and may launch multiple kernels.
    • Fill kernel: numeric keys hash/find their representative again, decrement a cursor, and scatter row IDs in hash_csr_build_fill_kernel. The cached variant reads the representative instead. Cursor updates produce the final offsets in the same kernel.
    • Join: hash_csr_probe_count_kernel fuses probe hashing, lookup, and match counting. A separate device scan computes output offsets; hash_csr_retrieve_kernel then expands ranges into pairs.
    • Groupby: a reduction kernel indirectly loads payloads through the CSR row IDs and aggregates each segment. The example uses SUM. “Gather” here is an in-kernel load, not a separate gather kernel or temporary value array. It consumes the shared CSR, not the join output.

    The execution strip shows the main data path. Initialization, allocation, and size-transfer plumbing are omitted. Boundaries are stream-ordered dependencies, not necessarily host synchronizations. Join and groupby are separate consumers of the CSR, not consecutive GPU stages.

    Example & conventions

    Build rows r0…r5: (A,12), (B,7), (A,8), (C,5), (B,3), (A,10). Probe rows p0…p2: B, A, D. All keys and values are non-null.

    • Fixed illustrative 32-bit hashes A→0xECC1EF1D, B→0x62F50105, C→0x0BEF92C6 show mixed bits across the whole word. They are chosen so that modulo 12 gives 1, 1, 6, preserving the A/B probe collision. These are not cuDF’s real hash outputs. Each displayed fingerprint shows its first and last three bits; the ellipsis hides the 23 middle bits, which may contain both zeros and ones.
    • One possible execution chooses representatives r0, r1, r3. Threads race using a device-scoped atomic compare-and-swap (CAS) on 32-bit slots in global memory. The first row to claim an empty slot becomes that key’s representative; equal rows reuse its stored row index. A collision with a different key continues probing. The winner is scheduling-dependent, not necessarily the lowest row index. This is distinct from the warp-aggregated atomic add that counts group members. See hash_table_ref::insert.
    • The packed slot combines two independently sourced fields. Its 29 high bits retain part of the original hash as a fingerprint: a quick mismatch filter that avoids loading and comparing unrelated keys. Its three low bits identify the representative build row, which locates both the original key and the group’s CSR segment. A fingerprint match still requires a full key comparison; it is not proof of equality. The row bits are neither hash bits nor a hash-table slot number.
    • For C, hash = 0x0BEF92C6 and the representative is r3. Retain the 29-bit fingerprint 00001011111011111001001011000, discard the hash’s low bits 110, and replace them with row index 011. Thus (0x0BEF92C6 & ~7) | 3 = 0x0BEF92C3. The full hash still determines the starting slot; only its stored representation is packed.
    • Any similar-looking patterns in the fingerprint and row bits are coincidental, not duplicated information. The low field comes from the representative row index, never from copying fingerprint bits. For example, B’s original low hash bits 101 are replaced by row index 001.
    • The six-row diagram shows the resolved stored word for each input, not six separately stored entries. Duplicates reuse the winning representative: r2 and r5 use r0’s bits 000; r4 uses r1’s bits 001. A resolves to 0xECC1EF18, B to 0x62F50101, and C to 0x0BEF92C3: only three directory entries.
    • Six build rows (indices 0–5) need three row bits. In general, bit_width(N) row bits leave 32 − bit_width(N) fingerprint bits. This keeps the all-ones row index outside [0, N), so the all-ones 32-bit slot can represent empty. The key itself stays in the original row, not in the packed slot.
    • Counts include a trailing zero. An inclusive scan creates cumulative ends; atomic decrement-and-scatter transforms these into exclusive starts. Nonrepresentative rows retain zero-length segments.
    • Numeric keys find their representative again during fill. Keys containing strings or lists cache the representative to avoid repeating costly hashing and comparisons.
    • In groupby, segment lengths give COUNT; reducing each segment’s payloads can compute SUM, MIN, or MAX. This example uses SUM and shows only occupied groups.
